# Schema-2 capability foundation

The capability engine/editor contract below is exercised by registered original family scenarios and actual private adapter checks; see the precise [coverage and source blockers](capability-coverage.md). It does not certify all official subclasses. Explicit progression supports total levels 1–20, declared multiclassing, source-owned tiered spell pools and editable casting loadouts. Equipment state and combat simulation remain outside this evaluator.

## Version boundary

`schemaVersion: 2` requires `capabilities: {version: 1, required: [...]}`. Supported required names are `choices`, `modifiers`, `casting`, `editions`, `resources`, `traits`, `proficiencies`, `configuration`, `languages`, `spell-pools`, `multiclass`. Unknown required names or versions fail import. Each capability-bearing definition has explicit `edition: "2014" | "2024"`. A schema-2 build pins `rulesProfile: {edition, evaluator: 2}`; absent keys never infer a saved-character upgrade. Classes intended for evaluator 2 should declare `capabilities`, even if only `{edition: "2014"}`.

`RulesEngine.evaluate(_:in:through:)` and `advance(_:in:)` retain their signatures. A legacy class with an absent profile still uses unchanged schema-1 replay, including in a mixed snapshot. `CapabilityEngine.evaluate` validates the supplied record before applying rules; invalid structural data returns `cap-invalid-content` with no calculated totals. Draft choices remain savable: missing picks are evaluation issues, not import errors.

Library structural budgets apply independently to each installed pack and pinned character snapshot, with the same checks before save and load. Accumulating valid characters does not exhaust one aggregate pack budget. Library version and duplicate character identity checks also run before writing; atomic saves and previous-file backups remain unchanged.

`ContentPack.sample()` loads the unchanged original schema-1 sample; `capabilitySample()` loads the separately generated original Trail Warden. AppStore installs the second sample when absent without rewriting any character snapshots. Source-qualified catalog identities include capability groups, options, grants, configurations, policies and their references. Same names do not imply shared rules.

## Choices and replay

`LevelChoice.capabilities` stores cumulative dictionaries `groups`, `spells`, `prepared`, and a `configurations` list. Each level stores its own choices. Earlier edits re-evaluate the whole history. `CapabilityChoiceGroup.counts` and `replacementLimits` are level-indexed totals/maximum removals (first element is level 1). `locked` forbids replacements. Unknown tracks, wrong counts, prerequisites, duplicate nonrepeatable ownership and exclusive option variants produce build issues.

Option IDs are canonical across independent tracks. A nonrepeatable option cannot double-grant via a bonus track. Repeatable options have per-track/per-position occurrence grant identity and additive grants stack per occurrence; proficiency ranks still take the maximum rather than adding. Authors must use distinct canonical option IDs for different parameter variants, such as separate skills.

- `requiredOptionID`: the group must include this option unless another track already owns it, in which case an alternative is allowed.
- `requiredOptionIDs`: the group must include at least one member of this family; owning a different family member elsewhere does not waive the requirement. Useful for mandatory skill-specific variants.
- `waiveRequiredFamilyIfOwned: true`: explicitly permits another eligible option when an accepted family member is owned in another track. Without this flag the family remains mandatory. Shared canonical IDs still prohibit duplicate ownership.
- `requirementTiming: "acquisition"` checks mandatory option/family alternatives only on the first nonempty acquisition row. Default `"ongoing"` (including absent data) preserves the prior continuous requirement. Earlier edits still replay the original acquisition; the selected locked bonus cannot change, but the original separately purchased family member can later be replaced if it is not an actual prerequisite.
- `exclusiveGroup` on options prevents incompatible variants being owned together.
- `exclusiveGroupExceptions` on a choice track explicitly permits an additional distinct variant of the named family across tracks. It does not permit two variants within that track or duplicate nonrepeatable canonical IDs. Ordinary tracks remain mutually exclusive with each other, and the exception is order-independent. The converter grants this exception only to the Cursed bonus Presence track, not ordinary Aspect purchases or Formless alternatives.

`RulePredicate` is closed typed data: `all`, `any`, `not`, `level`, `ability`, `selection`, `proficiency`, `configuration`, `subclass`. `key` names the referenced item; `minimum` supplies an ability/level threshold; composites use `children`. No strings execute as expressions. Selection dependencies are grounded from valid roots, including grant-derived proficiency. Current-level ASI cannot fund that level's capability prerequisite. Selection/configuration cycles and excessive predicate depth/fanout fail import.

Ordinary feat `abilityMinimums` also use capability-adjusted historical scores before the choice. Earlier retained ability grants can qualify; the current feat's boost or capability grants and newly acquired same-level options cannot fund its prerequisite. Earlier edits replay these checks. `RulesEngine.subclassUnlockLevel(for:build:in:)` is shared by the native editor and evaluator, including explicit edition adapters; premature saved subclass choices remain visible for correction and are not silently removed.

Configurations describe declared conditions, not combat state. Their `prerequisite` can require another configuration; `exclusiveGroup` prohibits simultaneous alternatives. Invalid configuration effects are removed and reported. The editor exposes controls and shows inactive tracks/policies explicitly so retained choices can be cleared.

## Grants and calculations

`CapabilityGrant` uses `id`, `kind`, optional `level`, `condition`, `target`, `value`, `rank`, `ability`, `text`, `recovery`. Kinds: proficiency, skillAbility, skillBonus, armorFormula, armorBonus, hitPoints, initiative, speed, speedBase, size, abilityScore, trait, resource, spell, language, manual, unsupported.

### Languages and edition-aware creation

Declare `languages` in the required capability names when authoring semantic language grants. A `language` grant's `target` is an authored canonical display name (1–120 characters, trimmed, no control characters), not a reference to the standard-choice pool. This allows original or exotic fixed languages without making them available as 2024 creation picks. Use the same exact spelling for the same language across sources. Fixed grants, including ordinary feature options that incidentally grant languages, deduplicate by name; their level/condition controls when they appear. Later conditional grants never invalidate an earlier learned copy, and removing a form does not remove another source's copy.

For actual language-selection slots, mark an ordinary capability group `languageChoices: true`. Each option must grant exactly one unconditional language at level 1, with no repeatability or unrelated effects. Options in that group name distinct languages; authored group counts, conditions, unlocks, replacement limits and locking control acquisition. Two selected language slots cannot spend choices on the same language, including overlap with 2024 standard creation selections. Ordinary feature choices are not language-selection slots and may grant overlapping fixed languages without being rejected. Unknown option IDs and earlier edits use normal historical replay validation.

2014 has no automatic Common or universal two-language allocation: species/background definitions author fixed grants and selection groups explicitly. The bundled **Old Road Wayfarer / Old Roadfolk / Old Road Guide** fixture grants Common and Road Cant from species plus one background language choice. Any retained `build.languages` values are preserved but require explicit review/clearing; they are not silently converted. 2024 and schema-1 keep Common plus two distinct selections from `pack.languages`. That list remains only the standard creation-choice pool, excludes Common, and is never expanded by fixed language grants. `CharacterSummary.languages` supplies both the native summary and printable sheet. Older pinned snapshots remain unchanged; installing the newer examples/converter output does not migrate them.

`speedBase` replaces the species walking speed before additive `speed` modifiers; use mutually exclusive predicates for alternative forms. `size` supplies a canonical size label (Tiny through Gargantuan), reflected in `CharacterSummary.size` and the printable size field. A `trait` with a `value` projects a calculated fact as `text: number`, useful for counts or secondary movement rates without claiming combat execution. Generic configuration controls activate these effects; no class-name special cases exist.

`RuleValue` combines bounded `base`, ability modifiers from `abilities`, `levelMultiplier`, `proficiencyMultiplier`, a level-indexed `table`, and optional `minimum`. Class/subclass-owned level references use that class's current historical level, not acquisition or total level; species/background/feat references use character level. Proficiency always uses total character level. Tables support up to 20 explicit rows. An absent active value/group/policy row blocks completion rather than extrapolating. Ability-score grants resolve before dependent totals; HP recalculates Constitution retroactively across every class's die, followed by defenses/initiative and casting values. Armor formulas select the best alternative before additive armor bonuses. No spending, rests or combat actions are simulated.

`abilityCap` grants declare an ability `target` and fixed `value.base` from 20 to 30; no dynamic expression is permitted for a cap. Caps use the highest applicable maximum, never add together. Every historical row checks its scores against its own active caps before continuing; a later cap cannot repair an earlier invalid score. Default maximum remains 20. Class `progression.improvement` rows are authoritative, and feat `repeatable: true` is explicit data, not inferred from its name. Repeatable feat scalar benefits and grants apply per acquisition with distinct grant identities; shared choice tracks remain canonical tracks, not automatically duplicated choices.

Proficiency grants also accept `save.str` through `save.cha`, and `all-saves`. These ranks are merged with class starting saves and projected into native summary/PDF values; saving-throw keys never become skill names.

Proficiency ranks are none/half/proficient/expertise; half rounds down and expertise doubles proficiency. `all-skills` is supported for proficiency grants. Resource grants expose maximum/recovery, never current expenditure. `trait` is displayed supported information; `manual` explicitly identifies unevaluated mechanics; `unsupported` blocks the selected build. A missing/unavailable spell reference is never fabricated.

Grant IDs identify nonstacking ownership across tracks. Conflicting grant definitions fail validation within their applicable scope. Explicit edition adapters contain `edition`, `canonicalID`, `label`, `replacementGrants`, optional `subclassLevel`; compatibility is never inferred from names. An adapter replaces capability grants for the target edition. It does not translate arbitrary legacy text or invent replacement choices.

## Casting policies

### Source-owned pools and current preparation (I3)

New casting fields require `spell-pools` in the pack's required capabilities; omission fails semantic import validation. Older evaluators reject this required capability instead of silently ignoring mechanics. Old pinned schema-1 and schema-2 snapshots remain readable, including historical preparation. No installed revision rewrites them.

Subclass policies declare `legacyClassCasting: "preserve" | "replace"` to distinguish independent sources from replacement. `preserve` keeps legacy class spell/cantrip acquisition, source abilities and historical validation; `replace` explicitly retains the previous replacement behavior. Absence also retains that historical behavior, so old pinned definitions do not change when unrelated new-capability content is added to a combined library. This optional field requires `spell-pools`, follows the policy through catalog qualification and save/reload, and is not inferred from the combined pack's capability union. If a subclass has multiple policies, all must declare `preserve` to be fully additive; any replacement/default policy retains replacement ownership. Class-owned casting policies still own the class tracks. Ascended explicitly replaces and conditions the existing known policy off while activating its editable preparation policy; independent Arcanum policies declare preserve.

`DefinitionCapabilities.spellPools` is an optional array of `{id, name, kind, recovery, capacities, condition?}`. Kinds are `ordinary`, `pact`, `limited`, `custom`. `capacities` has 1–20 exact level rows of tier-to-capacity objects, for example `[{"1":2}, {"1":3}, {"1":4,"2":2}]`. Tiers are 1–9, capacities 0–100; `{}` means zero capacity, while a missing active row is unsupported. Recovery and stable identity are mandatory. Conditions/unlocks use existing replay facts. Pool IDs are unique and source-qualified in snapshots; pools never merge by name or recovery. Multiple policies can reference the same pool without duplicating capacity. Inactive referenced pools block completion.

Additional `CastingPolicy` fields:

- `poolIDs`: declared pools in the owning definition/class scope. Cantrips and at-will sources need no pool.
- `loadout: "editable" | "retained"`: editable applies only to book/prepared acquisition. Retained lists obey historical replacement limits even if their displayed name is Prepared. Absence retains old schema-2 semantics.
- `preparation`: bounded `RuleValue` allowance, instead of `preparedCounts`, e.g. `{abilities:["int"], levelMultiplier:1, minimum:1}`. Source scores resolve after historical ability effects. Prepared-list policies can use `counts` as the allowance.
- `alwaysGrantedSpellIDs`: unconditional additional spells that never spend acquisition/preparation picks. Prepared/book policies label these always prepared. Use existing spell grants for level-dependent/conditional additions rather than an all-level list.

`CharacterBuild.castingLoadouts` is current configuration keyed by pinned policy ID. Book `LevelChoice.capabilities.spells` remains historical learned membership, validated at every level; loadout edits cannot erase it or legalize earlier mistakes. A prepared-list source chooses from its available list, not a permanent book. Preparation checks duplicates, eligibility and the declared allowance. Empty/incomplete loadouts remain savable drafts. Unknown/inactive keys remain visible for explicit review/clearing; retained sources cannot accept loadouts.

Missing keys seed from historical `prepared` (book) or `spells` (prepared list) without mutating history; explicit empty lists do not fall back. Earlier `through:` evaluation uses historical seeds rather than today's preparation. Native Build edits current preparation only at the latest level; book acquisition remains level-by-level. Found-spell copying beyond authored acquisition counts is not implemented.

`CharacterSummary.spellPools` exposes pool/owning source identity, kind, name, recovery and `[Int:Int]` capacities. `castingSources` exposes policy/source identity, ability, DC/attack, access ceiling, acquisition mode, available/learned membership, selected loadout, allowance, linked pools and classifications. Spell grants with explicit `ability` receive source summaries too. Legacy class casting plus innate casting retains both abilities. Legacy `slots`/`slotLevel` fields remain unchanged; scalar DC/attack become nil when multiple abilities make one number misleading.

Native Sheet/PDF consume these projections. The form's nine tier fields show exactly one ordinary pool, never pact/custom/limited pools or a sum of independent pools. Supplements label every pool/source and preserve all spells/classifications beyond 30 form rows. Legacy-only form output keeps its uniform pool. No spending/rest simulation occurs; higher capacity never unlocks knowledge.

### Verified common arithmetic, not inferred class rules

The original Notebook Keeper uses full ordinary capacity rows verified from [SRD 5.2.1](https://media.dndbeyond.com/compendium-images/srd/5.2/SRD_CC_v5.2.1.pdf), printed page 77, and [SRD 5.1](https://media.wizards.com/2023/downloads/dnd/SRD_CC_v5.1.pdf), page 52. Its two-spell acquisition is deliberately **not** a full Wizard implementation. Registered twenty-row checks also verify half-caster tables (5.2.1 page 53 / 5.1 page 30) and pact tables (5.2.1 page 71 / 5.1 page 46). Revised Paladin has level-one capacity; legacy Paladin does not. Single-class tables are explicit, not multiclass rounding.

Revised Wizard preparation counts are `[4,5,6,7,9,10,11,12,14,15,16,16,17,18,19,21,22,23,24,25]` (5.2.1 page 77); legacy preparation is `max(1, Wizard level + INT modifier)` (5.1 page 53). Book acquisition and preparation stay separate. Revised Warlock's retained list is labeled Prepared but replaces one spell upon gaining a Warlock level (5.2.1 page 72): author retained, not editable. Arcanum is independent limited capacity, not higher pact slots. No class-name switch or automatic full/half/fractional inference exists. Fractional checks use original custom rows; unsupplied commercial subclasses remain uncertified. These sources do not permit publishing private descriptions or claiming complete official content coverage.

### Historical schema-2 behavior

`CastingPolicy` declares `id`, `name`, `mode`, `ability`, exact eligible `spellIDs`, `counts`, `maximumSpellLevels`, optional `replacementLimits`, `preparedCounts`, `condition`, `text`. Modes: known, prepared, book, granted, ritual, limited, atWill. Counts are cumulative; prepared/ritual selections may change without a known-spell replacement charge. Book acquisition (`spells`) and preparation (`prepared`) are independent, and preparation must be a distinct subset of the acquired book.

A policy condition controls whether the selection track is active. To replace class-known casting at subclass unlock, condition the known policy with `not(subclass: id)` and define the prepared policy on that subclass. Historical rows retain their prior known choices; the new row clears the inactive track and fills preparation. Class and policy lists remain separate: adding an expanded list to one policy must not broaden another subclass's list. Temporary casting availability, expenditures and ritual execution are not combat simulation; do not model temporary inability to cast by deleting known choices.

Additional active spell grants do not consume `known` or `prepared` policy choices. A selection that tries to count one produces `cap-casting-granted-*`; retain its grant and select another eligible spell. Access to a granted spell above the current uniform slot level does not increase slots or change that spell's level.

Spell grants may declare `spellMode: granted | prepared | atWill | limited | ritual` (absent means granted). This supplies an explicit roster classification; it never simulates casting or expenditure. Multiple active grants retain their classifications. An always-prepared grant is labeled `Prepared (granted)` and remains additional to preparation counts.

Before I3, simultaneous policies with different casting abilities blocked completion with `cap-casting-abilities`. Current evaluation instead exposes each source's ability/DC/attack and leaves the single form header blank when multiple abilities would make it misleading; see the source-owned contract above.

## Multiclass contracts (I4)

`multiclass` is a required capability for class policies, explicit `LevelChoice.classID` and canonical feature identities. Older evaluators reject the pack rather than ignoring class history. Absent historical class IDs still mean `CharacterBuild.classID`, never the previous row. New native builds and advancement under this contract write explicit IDs. Starting identity must match level one. Schema-1 and older pinned schema-2 definitions do not acquire new policies by importing unrelated packs.

`ClassDefinition.multiclass` declares:

- `canonicalID`: stable across editions/revisions; intentionally not source-qualified. Two distinct selectable definitions with this identity cannot be combined, even with edition adapters.
- `prerequisites`: bounded ability predicates combined with `all`/`any`. On entry into a new class, every current class and the new class are checked against the preceding level's fully calculated scores. A new class's own grant or same-level feat cannot repair entry.
- `startingProficiencies` (optional), `laterProficiencies`: fixed proficiency grants, not saving throws/effects. Only the starting class supplies its existing saving throws and `skillCount` choices. Optional `laterSkillCount` selects new skills from its `skillPool`, saved in the entry row's `multiclassSkills`.
- `casting`: `{kind, divisor, rounding, startsAt, poolIDs, reciprocalSlotUse}`. Kind is `ordinary`, `independent` or `none`; divisor is 1–20, rounding `up`/`down`, and `startsAt` the class-level acquisition threshold. Ordinary policies name ordinary pool IDs, including a subclass-owned pool if appropriate. Missing policies on a selected custom caster produce an explicit incompatibility issue.

Later-class skill picks are also checked against the preceding row's resolved proficiency ranks, including accepted conditional/option grants with that row's final ability scores. Already-proficient/expert skills cannot spend a new-skill choice; half proficiency is not full proficiency. Current-row duplicate checks remain in the ordinary replay. Future grants cannot retroactively invalidate an earlier entry choice.

**Track ownership boundary:** authors opting classes into multiclassing must use distinct IDs for class-owned groups, configurations and casting policies, across those namespaces and across each class/subclass scope. Conflicts between opted-in classes or between an opted-in class and common species/background/feat tracks reject an authored source pack with an error naming the ID and owners. Intentional common canonical tracks still share one common owner. Existing all-nonopt single-class packs keep their local IDs. Combined snapshots defer this ownership check until a multiclass combination is selected; only participating classes (plus common tracks) are checked, so merely installing an unrelated colliding class cannot invalidate a pinned single-class build. Advancement, record validation and replay reject ambiguous selected ownership rather than aliasing or silently choosing an owner. Source qualification still separates the same local ID from different sources; no saved IDs are renamed.

`RulesEngine.advance(_:in:classID:)` selects the advancing class; the old overload continues the last class. It checks the existing build, total cap, selected class's explicit progression limit and entry prerequisites. The next row inherits that class's acquisition choices and the latest common choices; another class's tracks remain on their own rows. A row editing another class's tracks is flagged rather than silently accepted. Earlier edits never delete saved choices. Current casting loadouts remain independent and can be edited on the final row even when it advances a different class.

The same chronological evaluator handles creation, HP, feats and all capabilities. `Multiclassing.timeline` projects authored class-level thresholds, predicates and exact tables onto character-level replay; it does not evaluate or aggregate separate finished sheets. Class-local subclass predicates retain owning-class context even when local subclass IDs match. Total PB and chronological ability prerequisites remain shared. Missing rows remain missing, not extrapolated. Feature prose can declare `canonicalID` to render once across sources; same canonical grant IDs remain nonstacking. This is not combat execution of Extra Attack or Channel Divinity.

Ordinary pools combine only when more than one class has active declared Spellcasting. Each class contributes according to its explicit divisor/rounding; access/known/prepared ceilings remain class-local. Martial plus one caster retains that caster's own table. Pact/custom/limited pools remain separate; reciprocal slot-use permission never merges capacity or recovery. Summary exposes ordered `classLevels` (features, subclass and casting-source IDs), `hitDice`, and the existing per-source casting summaries. Native Summary, factual Story context and PDF consume these facts. Long class labels use the existing PDF overflow mechanism; each die size appears in the multiclass supplement.

### Primary rule evidence and limits

Checked 2026-11-13: [SRD 5.2.1, Multiclassing, pp.24–26](https://media.dndbeyond.com/compendium-images/srd/5.2/SRD_CC_v5.2.1.pdf) distinguishes total-level proficiency, class advancement, starting HP and independent spell access; revised half-caster contribution rounds up. [SRD 5.1, pp.56–58](https://media.wizards.com/2023/downloads/dnd/SRD_CC_v5.1.pdf) and the [official 2014 Basic Rules, Spellcasting](https://www.dndbeyond.com/sources/dnd/basic-rules-2014/customization-options#Spellcasting) specify legacy half-caster rounding down. [Official 2024 Basic Rules, Spellcasting](https://www.dndbeyond.com/sources/dnd/br-2024/creating-a-character#Spellcasting) specifies one-third rounding down for its named fractional subclasses. These are data policies, not class-name switches.

The supplied legacy SRD/free Basic Rules omit commercial fractional-subclass contributions. Generic original fractional tests are not an audit or supplied pack for those legacy subclasses. No community quotation or Foundry implementation substitutes for primary evidence. Actual private Vessel evidence comes from its reviewed original PDF pages 2–3: explicit entry/exit prerequisites, reduced later training, independent capacity and reciprocal use; no ordinary contribution is inferred from its half-speed table.

## Presentation and copy review

Defaulted `CharacterSummary` additions preserve legacy caller compatibility: `languages`, `proficiencyRanks`, `skillModifiers`, `traits`, `resources`, `provenance`, `supportDiagnostics`, `spellLabels`, `activeGroupIDs`, `activePolicyIDs`, `castingAbility`. SwiftUI and `PrintableSheet` consume these outputs, including partial/expert skill values and policy labels. Sheet notes identify selected configurations and leave untracked state blank. Core projection tests do not prove native PDF rendering or device layout.

`RulesUpgrade.copy(_:) throws -> CharacterRecord` validates the input and produces a distinct build ID and pinned evaluator-2 snapshot, preserving level history, story and portrait. `upgradeReview` blocks advancement until explicit review; the source record is never overwritten. AppStore saves only the returned copy. This does not convert a private class into a newly supported ruleset automatically.

## Authoring and verification

Keep Swift contracts, `scripts/build-schema.mjs`, `scripts/build-example-pack.mjs`, generated schema/resources and this guide synchronized. `PackValidator` semantic checks add bounded counts, identity/reference integrity, grant consistency, dependency cycles and record-size limits beyond JSON Schema. Tests use original data and the standalone `swift run FolioChecks` runner. Register every new scenario there. Native compilation and `bash scripts/check-presentation.sh` are separate gates; actual private acceptance reports absent inputs explicitly and does not substitute for native/device/PDF verification.
